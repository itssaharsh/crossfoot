What the published file looks like (`data/files/panola.csv`, 783 rows; look at it yourself): columns `county, precinct, office, district, party, candidate, votes, absentee, early_voting, election_day`. "Registered Voters" rows carry only `votes`; "Ballots Cast" rows carry the parts. Labels differ from the scan's: the scan prints a ticket ("A/B (PARTY)") or "Write In" above a name, the file has one name and a party column; capitals and spellings vary, and one office name appears in two spellings. Some contests on the last page cover only some precincts (the scan blacks out the other cells and the file has rows only for some precincts, with a `district` value). EARLY is `early_voting`, ABSENTEE is `absentee`, PRECINCT is `election_day`, the small total under a column is `votes`.

Acceptance (REQUIRED):
- WHEN the audit runs THE SYSTEM SHALL match contests and candidates by normalised labels first, send only what is left to the model once per county as two lists, and check the answer in code (one-to-one; mapped pairs have close county totals); what cannot be matched is listed, never guessed
- The published file is a second reading of the same scan, and the audit uses it to know where to look, never what to write. WHEN a published value differs from the ledger's value THE SYSTEM SHALL look at that value on the scan once more (the loop's single-value re-read at 400 dpi or more, with `claude-sonnet-4.6`) before anything is concluded: IF the re-read gives the file's value and the sums hold with it THEN the ledger was wrong, the value is corrected with an event and there is no finding; IF it gives the ledger's value again THEN the finding stands. Re-reads may run up to three at a time with call starts at least 1.1 seconds apart.
- WHEN a published value still disagrees after that THE SYSTEM SHALL write a finding with: county, office, candidate, precinct, part (`votes`, `absentee`, `early_voting` or `election_day`), file value, scan value, kind (`file_row_fails_own_total`, `wrong_number`, `wrong_column`, `wrong_precinct`, `missing_row`, `extra_row`), status, the sums that decide it (each with its terms, the printed total, and whether it holds with the file's value and with the scan's value), page, block, the cell's box, the crop path, and `confirmed_by_person: false`
- Status rules, in code and tested: `settled_against_file` only when at least one printed total on the scan holds with the scan's value and fails with the file's value, and no printed total holds with the file's value and fails with the scan's; `document_inconsistent` when the scan's own printed totals disagree with each other at that cell (name which); `cannot_verify` when no printed total decides (a sum that fails with both values decides nothing) or the scan's value itself is in doubt. The row totals and the grand total count as printed totals: a small total that is hard to read is decided by them.
- AC-7: WHEN the corrected file is written THE SYSTEM SHALL change only cells whose finding is `settled_against_file`, keep every other byte of the published file, and write `changes.diff` (unified) for exactly those lines (tested with a small made-up file and ledger)
- Findings that describe one slip are grouped: a value sitting in the wrong part of the same precinct is one `wrong_column` group; the same values sitting under other precincts of the same row is one `wrong_precinct` group; give each group an id and keep the cell-level findings under it
- A published row whose own parts do not add to its `votes` is a `file_row_fails_own_total` finding whether or not the scan decides it; then the rules above give its status
- AC-2: `uv run crossfoot verify-known --county panola` compares the newest `findings.json` with `tests/known_panola.json` and exits non-zero if an expected finding is missing; it prints how many findings were expected, how many were found, and how many findings there are in all. The audit code must not read that file (a test checks that no module under `crossfoot/` except the `verify-known` command names it).
- `report.md`: plain words; counts by kind and status; then one section per group with the crop, the sums in words and numbers, the file's value and the scan's value; then what could not be verified and why. Follow the wording rule in AGENTS.md: these are transcription slips in a volunteer dataset, the scan is the source, no comment on any candidate, party or official, and nothing says a person has confirmed a finding.
- Policy (`policy.py`): one question, id `document_disagrees_with_itself`; the default answer is "follow the cells as printed and list the printed total as inconsistent", stored in `runs/<run_id>/policy.json` with `answered_by: "default, not yet confirmed by a person"`; `crossfoot policy set --answer cells|totals` stores a person's answer for later runs.
