# T05 Write up the recovery run and deal with the worst failure of the full run — M9
Context: the event asks for a run before a change and a run after it with the numbers compared. Repo root, branch main, BASE: the commit `pb.py task T05 start` recorded.
Read first: AGENTS.md, .prod-build/reports/T04.md, the newest `runs/<run_id>/summary.json`, crossfoot/agent.py, crossfoot/layouts/
Memory to apply: run `python3 .prod-build/pb.py mem find --terms "failure" "reread" "cost"` first.

Done when (REQUIRED): `docs/evidence/recovery.md` exists (step 6); the worst remaining failure of the full run is either fixed, with a second table added to `docs/evidence/before-after.md` (which already holds T02a's), or listed with its numbers under known limits in `hackathon.md`; `uv run pytest -q` passes.

Steps:
1. The run before is the newest full run under `runs/` (do not re-run it). From its `summary.json` and events, list the three most costly failures by a number that matters: cells that needed a re-read, cells left cannot_verify, false alarms in the audit (disagreements that turned out to be label or position mistakes of this program), or cost per county.
2. Look at the traces for the worst one. This session has the neatlogs MCP server (`search_traces`, `get_trace_context`). Find the span that shows the cause. Write down the trace id, the span and what it shows. If the MCP server is not available, read the run's events and say so.
3. Fix that one cause. Start with a failing test where the cause is a rule or a parsing bug.
4. Run the same counties again as the run after (same command, same models; at most two counties if the budget is tight: Panola plus the county where the failure was worst). Budget for this task: 3 dollars; check `crossfoot budget` before and after.
5. Add a second section to `docs/evidence/before-after.md` (keep T02a's): what failed, the trace id and span, the change (commit hash), then a table with both runs' numbers from their `summary.json` files (cells read, sums failing after the first read, cells re-read, cannot_verify, disagreements by status, model calls, metered cost, seconds). Only numbers that are in those files. Say plainly if the fix made something worse.
6. Add `docs/evidence/recovery.md`: one place in the run after where an action failed (a rejected accept, a re-read that still failed, a bad JSON answer) and what the agent did next, quoted from the run's events with their timestamps.

Constraints: one fix only. Do not tune prompts to the known Panola answers; the fix has to be about a cause, and `verify-known` must still pass without the audit reading the answer key.
